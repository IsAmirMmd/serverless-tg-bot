# بریف: چندکاناله کردن ربات و مدیریت کاربران از پنل

> وضعیت: **فازهای ۱ تا ۴ پیاده‌سازی شدند** (۲۴ مهر ۱۴۰۵ / 2026-10-15).
>
> **فاز ۵ (اشتراک با استارز) هم پیاده‌سازی شد:**
> - هر کانال یک تاریخ انقضا (`channels.expires_at`) دارد. خالی بودنش یعنی نامحدود.
> - کانال منقضی‌شده خودکار سرویس نمی‌گیرد.
> - پرداختی که خریدار قبل از داشتن کانال انجام بدهد، به‌صورت اعتبار ذخیره می‌شود و وقتی ربات را به کانالش اضافه کرد، روی همان کانال اعمال می‌شود.
> - تمدید از پنل با `openInvoice` انجام می‌شود.
> - یادآوری و اعلام انقضا هر روز با `.github/workflows/billing.yml` اجرا می‌شود.
> - برگشت استارز از تب پرداخت‌ها انجام می‌شود.
> - `AUTO_ACTIVATE_PAID` در `config.js` تعیین می‌کند که کانالِ کسی که پرداخت کرده خودکار فعال شود یا منتظر تأیید مالک بماند.
>
> گزارش جداگانه برای هر مدیر هنوز برای بعد مانده است.
>
> تصمیم‌های بخش ۹:
> ۱. کانال جدید را فقط مالک فعال می‌کند.
> ۲. کسی که ربات را اضافه کرده، بعد از فعال‌سازی مدیر کانال می‌شود.
> ۳. مدیران و بیننده‌ها فقط آمار می‌بینند. ستون‌های `signature` و `use_llm` ساخته نشدند.
> ۴. اشتراک و انقضا بعداً اضافه می‌شود.
> ۵. در کانال متوقف یا تأییدنشده، دکمه‌های لایک کار نمی‌کنند.
> ۶. فعلاً به کلید OpenRouter نیازی نیست.

## ۱. هدف

ربات یک محصول باشد: هر صاحب کانال (مشتری) بتواند ربات را روی کانال خودش داشته باشد و فقط آمار و گزارش‌های کانال خودش را در پنل ببیند. **مالک** (ADMIN_ID) از داخل پنل کانال‌ها را فعال کند، کاربر جدید اضافه کند و دسترسی‌ها را مدیریت کند. برای اضافه کردن مشتری جدید نباید نیازی به تغییر کد یا deploy باشد.

## ۲. وضعیت فعلی (چیزهایی که باید عوض شوند)

| موضوع | الان | مشکل در حالت چندکاناله |
|---|---|---|
| دسترسی به پنل | فقط `ADMIN_ID` (`requireAdmin`) | مشتری‌ها اصلاً دسترسی ندارند |
| کانال‌ها | جدولی برایشان وجود ندارد. هر کانالی که ربات را ادمین کند پردازش می‌شود | **هر کسی ربات را به کانالش اضافه کند، سرویس رایگان می‌گیرد.** کنترلی وجود ندارد |
| یکتایی رأی | ایندکس یکتا روی `(music_id, user_id)` | `music_id` همان `message_id` پست است و **فقط داخل یک کانال یکتاست**. پست شماره ۱۲۰ در دو کانال مختلف رأی‌هایشان قاطی می‌شود |
| `channel_id` در `likes` | بیشتر ردیف‌های قدیمی (import شده) `NULL` هستند | بدون پر کردن آن‌ها، داده کانال شما در فیلتر کانال دیده نمی‌شود |
| تنظیمات | `SIGNATURE`، `USE_LLM` و پیام‌های خطا سراسری‌اند و به `ADMIN_ID` می‌روند | هر کانال امضا و تنظیمات خودش را می‌خواهد. خطای کانال مشتری نباید فقط برای مالک برود |
| endpointها | آمار کل جدول `likes` را برمی‌گردانند | باید همیشه به کانال‌های مجاز همان کاربر محدود شوند |

## ۳. نقش‌ها

| نقش | کیست | چه می‌بیند و چه می‌کند |
|---|---|---|
| **مالک** (owner) | `ADMIN_ID` در `config.js` | همه کانال‌ها و همه داده‌ها. فعال یا متوقف کردن کانال، اضافه و حذف کاربر، ساخت لینک دعوت |
| **مدیر کانال** (manager) | مشتری | آمار و گزارش کانال(های) خودش. در فاز بعد می‌تواند تنظیمات کانالش (مثلاً امضا) را عوض کند |
| **بیننده** (viewer)، اختیاری | همکار مشتری | فقط دیدن آمار همان کانال |

یک کاربر می‌تواند به چند کانال دسترسی داشته باشد، و یک کانال هم می‌تواند چند کاربر داشته باشد.

## ۴. مدل داده (تغییرات `tgcloud/schema.js`)

```js
// کانال‌هایی که ربات در آن‌ها ادمین است
export const channels = table('channels', {
  chat_id:    text('chat_id').primaryKey(),          // '-100…'
  title:      text('title'),
  username:   text('username'),                      // برای لینک t.me/<username>/<id>، اگر کانال عمومی باشد
  status:     text('status').notNull().default('pending'), // pending | active | paused
  signature:  text('signature'),                     // جایگزین SIGNATURE سراسری
  use_llm:    boolean('use_llm').notNull().default(false),
  added_by:   integer('added_by'),                   // کاربری که ربات را به کانال اضافه کرد
  expires_at: integer('expires_at', { mode: 'timestamp' }), // برای اشتراک؛ فعلاً اختیاری
  created_at: integer('created_at', { mode: 'timestamp' }).default(sql`(unixepoch())`),
});

// چه کسی به کدام کانال دسترسی دارد
export const channel_members = table('channel_members', {
  id:         integer('id').primaryKey({ autoIncrement: true }),
  channel_id: text('channel_id').notNull(),
  user_id:    integer('user_id').notNull(),
  user_name:  text('user_name'),
  role:       text('role').notNull().default('manager'), // manager | viewer
  added_at:   integer('added_at', { mode: 'timestamp' }).default(sql`(unixepoch())`),
}, (t) => ({ uniq: uniqueIndex('uidx_members_channel_user').on(t.channel_id, t.user_id) }));

// لینک‌های دعوت (یک‌بارمصرف)
export const invites = table('invites', {
  code:       text('code').primaryKey(),             // تصادفی، مثلاً ۱۶ کاراکتر
  channel_id: text('channel_id').notNull(),
  role:       text('role').notNull().default('manager'),
  created_by: integer('created_by').notNull(),
  used_by:    integer('used_by'),
  expires_at: integer('expires_at', { mode: 'timestamp' }),
  created_at: integer('created_at', { mode: 'timestamp' }).default(sql`(unixepoch())`),
});
```

در جدول `likes`:
- یک ایندکس یکتای جدید روی `(channel_id, music_id, user_id)` ساخته شود. ایندکس قدیمی `uidx_likes_music_user` بعد از مهاجرت با `.deprecated()` حذف شود.
- `ON CONFLICT (music_id, user_id)` در `lib/likes.js` به `ON CONFLICT (channel_id, music_id, user_id)` تغییر کند.
- `channel_id` همیشه پر شود. در `callback_query` همین الان پر می‌شود، ولی import باید یک کانال مشخص بگیرد.

### مهاجرت داده‌های فعلی (یک‌بار، قبل از هر چیز)

```
npm run sql -- "UPDATE likes SET channel_id = '-1001797602120' WHERE channel_id IS NULL OR channel_id = ''"
npm run sql -- "INSERT INTO channels (chat_id, title, username, status) VALUES ('-1001797602120', 'chosi', 'chosi_chnl', 'active')"
```

بعد از این دو دستور، کانال شما اولین کانال فعال است و همه داده‌های فعلی به آن تعلق می‌گیرد. (عنوان دقیق کانال را بعداً `getChat` به‌روز می‌کند.)

## ۵. جریان‌ها

### ۵.۱ اضافه شدن ربات به یک کانال جدید
1. مشتری ربات را ادمین کانالش می‌کند (با دسترسی post و edit و delete).
2. handler جدید `handlers/my_chat_member.js` این رویداد را می‌گیرد. اگر ربات ادمین شده باشد، در `channels` یک ردیف با `status = 'pending'` ثبت می‌کند و به مالک پیام می‌دهد: «ربات به کانال X اضافه شد. فعال شود؟» (دکمه inline فعال‌سازی، یا از پنل).
3. تا وقتی کانال `active` نشده، `channel_post` پست‌هایش را **پردازش نمی‌کند**. این همان کنترل فروش است.
4. اگر ربات از کانال حذف شود، همین handler `status = 'paused'` می‌کند.

> یادآوری: نوع آپدیت `my_chat_member` باید در webhook فعال باشد. پلتفرم این را از روی فایل‌های `handlers/*` تنظیم می‌کند. بعد از push، با `npx tgcloud webhook` بررسی کنید.

### ۵.۲ اضافه کردن کاربر جدید از پنل مالک (روش پیشنهادی: لینک دعوت)
1. مالک در پنل، تب **«کاربران و کانال‌ها»**، کانال را انتخاب می‌کند و «ساخت لینک دعوت» را می‌زند (نقش: مدیر یا بیننده، با انقضای پیش‌فرض ۷ روز).
2. endpoint ‌`ownerCreateInvite` یک کد تصادفی می‌سازد و لینک `https://t.me/<bot_username>?start=inv_<code>` را برمی‌گرداند. پنل دکمه «کپی» و «اشتراک‌گذاری» (`Telegram.WebApp.shareMessage` / `openTelegramLink`) دارد.
3. مالک لینک را برای مشتری می‌فرستد. مشتری لینک را باز می‌کند و `/start inv_<code>` به ربات می‌رسد.
4. `handlers/message.js` کد را بررسی می‌کند (وجود دارد، استفاده نشده، منقضی نشده). بعد:
   - ردیف `channel_members` را می‌سازد و `used_by` را ثبت می‌کند.
   - `setChatMenuButton` را برای چت همان کاربر روی Mini App تنظیم می‌کند. دکمه «پنل» فقط برای اعضا دیده می‌شود.
   - به کاربر می‌گوید «دسترسی شما به کانال X فعال شد» و یک دکمه «باز کردن پنل» می‌فرستد.
   - به مالک خبر می‌دهد: «@user به کانال X اضافه شد».

**چرا لینک دعوت:** مالک لازم نیست شناسه عددی کاربر را پیدا کند. کاربر خودش ربات را start می‌کند، پس ربات اجازه پیام دادن به او را دارد. لینک هم یک‌بارمصرف و منقضی‌شونده است.

**روش جایگزین، اضافه کردن مستقیم:** مالک شناسه عددی کاربر را وارد می‌کند (`ownerAddMember`). شرطش این است که کاربر قبلاً ربات را start کرده باشد، وگرنه `setChatMenuButton` و پیام خوش‌آمد با خطای 403 شکست می‌خورند. در این حالت پنل باید پیام «کاربر هنوز ربات را start نکرده» را نشان دهد.

### ۵.۳ ورود کاربر به پنل
1. کاربر از دکمه منو یا `/panel` پنل را باز می‌کند.
2. endpoint ‌`me` نقش و کانال‌های مجاز او را برمی‌گرداند: `{ isOwner, channels: [{ chat_id, title, role }] }`.
3. اگر کاربر هیچ کانالی نداشته باشد، صفحه «دسترسی ندارید» نمایش داده می‌شود (همان حالت فعلی).
4. اگر چند کانال داشته باشد، بالای پنل یک **انتخابگر کانال** دیده می‌شود. مالک گزینه «همه کانال‌ها» را هم دارد.
5. همه جدول‌ها (رأی‌ها، گزارش کاربران، گزارش آهنگ‌ها) و کارت‌های آمار فقط داده همان کانال را نشان می‌دهند.

### ۵.۴ حذف دسترسی و توقف کانال
- مالک در پنل عضو را حذف می‌کند. ردیف `channel_members` پاک می‌شود و `setChatMenuButton` برای آن کاربر به `{ type: 'default' }` برمی‌گردد.
- مالک کانال را `paused` می‌کند. پست‌ها دیگر پردازش نمی‌شوند، ولی دکمه‌های لایک قبلی کار می‌کنند. اینکه آن‌ها هم متوقف شوند یک تصمیم است (بخش ۹).

## ۶. پنل (React، طراحی میرزا)

**برای همه اعضا:**
- انتخابگر کانال در هدر (با `.mz-select`، یا `.mz-tabs` اگر کانال‌ها کم باشند).
- همان سه جدول و کارت‌های آمار فعلی، محدود به کانال انتخاب‌شده.

**فقط برای مالک، تب جدید «کاربران و کانال‌ها»:**
- **جدول کانال‌ها:** عنوان (لینک به کانال)، وضعیت (`.mz-badge`)، تعداد اعضا، تعداد رأی‌ها، تاریخ اضافه شدن، و دکمه‌های فعال‌سازی و توقف.
- **جدول اعضا:** کاربر، کانال، نقش، تاریخ، و دکمه حذف (با تأیید `Telegram.WebApp.showConfirm`).
- **دکمه «کاربر جدید»:** یک فرم با انتخاب کانال و نقش، که لینک دعوت می‌سازد. گزینه دوم «افزودن با شناسه عددی» است.
- **لیست دعوت‌های فعال:** با امکان باطل کردن.
- همه جدول‌ها صفحه‌بندی و جستجو دارند (همان `DataTable` و `Pagination`).

## ۷. endpointها

همه از `ctx.initData.user.id` استفاده می‌کنند و **هیچ‌وقت** به شناسه کاربری که از `input` می‌آید اعتماد نمی‌کنند. هر `channelId` ورودی در سرور بررسی می‌شود.

| endpoint | دسترسی | کار |
|---|---|---|
| `me` | هر کاربر | نقش و کانال‌های مجاز |
| `adminSummary`، `adminLikes`، `adminUserReport`، `adminMusicReport` (موجود) | عضو کانال | ورودی جدید `channelId` (یا `'all'` فقط برای مالک)، و `WHERE channel_id = ?` |
| `ownerChannels` | مالک | لیست کانال‌ها با تعداد اعضا و رأی |
| `ownerSetChannelStatus` | مالک | `{ channelId, status }` |
| `ownerMembers` | مالک | لیست اعضا، صفحه‌بندی‌شده |
| `ownerCreateInvite` / `ownerRevokeInvite` / `ownerInvites` | مالک | مدیریت لینک‌های دعوت |
| `ownerAddMember` / `ownerRemoveMember` | مالک | افزودن مستقیم با شناسه، یا حذف |

helperهای مشترک در `lib/access.js`:

```js
export const isOwner = (ctx) => ctx.initData?.user?.id === ADMIN_ID;
export function requireOwner(ctx) { if (!isOwner(ctx)) throw new EndpointError('فقط مالک', { code: 'FORBIDDEN' }); }
// برای مالک همه کانال‌ها؛ برای بقیه، کانال‌های عضو. اگر channelId مجاز نباشد → FORBIDDEN
export async function requireChannel(ctx, channelId) { … }
```

## ۸. تغییرات ربات (handlers و lib)

- **`handlers/channel_post.js`:** اگر کانال در `channels` نیست یا `active` نیست، کاری نکند. `SIGNATURE` و `USE_LLM` را از ردیف همان کانال بخواند. خطاها برای مالک و مدیران همان کانال فرستاده شوند.
- **`handlers/my_chat_member.js` (جدید):** ثبت، فعال‌سازی و توقف کانال (بخش ۵.۱).
- **`handlers/callback_query.js`:** بدون تغییر منطق. `channel_id` همین الان ذخیره می‌شود و فقط کلید یکتا عوض می‌شود.
- **`handlers/message.js`:** مدیریت `/start inv_<code>`. دستور `/panel` برای همه اعضا (نه فقط مالک).
- **دستورهای ادمین (`/report`، `/backup`، `/import`، لایک فیک):** فعلاً فقط برای مالک. برای `/import` یک پارامتر کانال اضافه شود. در فاز بعد، `/report` برای هر مدیر روی کانال خودش کار کند.
- **`lib/dashboard.js`:** همه کوئری‌ها پارامتر `channelId` بگیرند. `withLinks` از `channels.username` استفاده کند و دیگر حدس «پرتکرارترین کانال» لازم نیست.

## ۹. تصمیم‌هایی که باید گرفته شوند

1. **کانالی که خودش ربات را اضافه کرده:** فقط مالک فعالش کند (پیشنهادی، برای کنترل فروش)، یا خودکار فعال شود؟
2. **کسی که ربات را به کانال اضافه کرده (`added_by`):** بعد از فعال‌سازی، خودکار مدیر همان کانال شود؟ پیشنهاد: بله.
3. **مدیران کانال:** اجازه تغییر امضا یا روشن کردن LLM را داشته باشند، یا فقط آمار ببینند؟
4. **اشتراک یا انقضا (`expires_at`):** همین فاز اضافه شود یا بعداً؟ اگر بله، کانال منقضی‌شده `paused` شود.
5. **کانال متوقف‌شده:** دکمه‌های لایک قدیمی کار کنند یا نه؟
6. **کلید OpenRouter:** مشترک برای همه (هزینه با مالک)، یا هر مشتری کلید خودش را بدهد؟

## ۱۰. فازبندی پیشنهادی

| فاز | محتوا | خروجی قابل تست |
|---|---|---|
| **۱. پایه داده** | جدول‌های `channels`، `channel_members` و `invites`، ایندکس یکتای جدید، و مهاجرت داده فعلی (بخش ۴) | `npm run sql` نشان می‌دهد همه رأی‌ها `channel_id` دارند |
| **۲. دسترسی** | `lib/access.js`، endpoint ‌`me`، و پارامتر `channelId` در endpointهای فعلی، با انتخابگر کانال در پنل | مالک «همه» و کانال خودش را می‌بیند. یک کاربر آزمایشی بدون عضویت FORBIDDEN می‌گیرد |
| **۳. مدیریت کاربران** | تب «کاربران و کانال‌ها»، لینک دعوت، `/start inv_…`، تنظیم دکمه منو برای عضو | با یک اکانت دوم: لینک دعوت ← start ← پنل فقط کانال خودش را نشان می‌دهد |
| **۴. کنترل کانال‌ها** | `my_chat_member`، وضعیت pending/active/paused، و تنظیمات هر کانال (امضا و LLM) | اضافه کردن ربات به یک کانال آزمایشی ← پیام به مالک ← فعال‌سازی از پنل ← پست پردازش می‌شود |
| **۵. اختیاری** | اشتراک و انقضا، گزارش و بکاپ برای هر مدیر، تنظیمات توسط خود مشتری | — |

استقرار هر فاز: `npm run update` (build، push و migrate). برای فاز ۱، قبل از migrate یک `/backup` بگیرید.
